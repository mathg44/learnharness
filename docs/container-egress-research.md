# Container-local egress enforcement research

This research supports issue #27. It is not a deployment runbook. The
proposed details below need the disposable verification described in the checklist.
No host firewall rules, host routes, or global Docker daemon network settings
are part of this design.

## Decision

Use a **namespace-local nftables guard**. A trusted guard container owns the
Docker network namespace and is the only container given `NET_ADMIN`; the
application shares that namespace but is unprivileged. The guard installs and
maintains an nftables `inet` output policy. An `inet` table processes IPv4 and
IPv6, and its output hook sees packets generated by local processes
([nft(8)](https://netfilter.org/projects/nftables/manpage.html#_ipv4_ipv6_inet_address_families)).
Docker documents `NET_ADMIN` as the capability for network-stack changes,
rather than requiring `--privileged`
([Docker: running containers](https://docs.docker.com/engine/containers/run/#runtime-privilege-and-linux-capabilities)).

This was selected over an explicit egress proxy because it can constrain
arbitrary application and browser traffic, including software that neither
supports HTTP proxy configuration nor consistently honors it. An explicit
proxy remains a valid, lower-privilege option only when every intended protocol
is proxy-aware and bypass-resistant. A Compose `internal` network removes its
external default gateway, but it does not itself force an application to use a
proxy or govern traffic once the proxy has accepted it
([Docker: networking in Compose](https://docs.docker.com/compose/how-tos/networking/#configure-the-default-network)).

## Researched facts

- Docker supports attaching one container to another container's network stack.
  In this mode, the joining container cannot independently configure hostname,
  DNS, port publishing, or network attachments
  ([Docker: networking overview](https://docs.docker.com/engine/network/#container-networks)).
  Compose also forbids a service from declaring both `network_mode` and
  `networks` ([Compose services reference](https://docs.docker.com/reference/compose-file/services/#network_mode)).
- Docker's embedded resolver is `127.0.0.11` on custom networks, forwards
  external lookups using host-configured resolvers, and remains the IPv4
  resolver address even in IPv6-only containers
  ([Docker: DNS services](https://docs.docker.com/engine/network/#dns-services)).
  Docker documents that DNS iptables rules for bridge networks are created in
  the container network namespace
  ([Docker and iptables](https://docs.docker.com/engine/network/firewall-iptables/)).
- nftables timeout sets support elements that expire. nftables base-chain
  priority is ascending, so lower numeric priorities run first
  ([nft(8): sets](https://netfilter.org/projects/nftables/manpage.html#_sets),
  [nft(8): chains](https://netfilter.org/projects/nftables/manpage.html#_chains)).
  Connection tracking can retain an established TCP entry for a long time; it
  is therefore not a permission system by itself
  ([nftables: connection tracking state](https://wiki.nftables.org/wiki-nftables/index.php/Matching_connection_tracking_stateful_metainformation)).
- Compose can wait for a dependency healthcheck. Its dependency `restart: true`
  applies to explicit Compose-controlled updates, not a container runtime
  restart after a crash
  ([Compose startup order](https://docs.docker.com/compose/how-tos/startup-order/)).
- Tailscale Serve is a reverse proxy to a local backend, including a localhost
  port ([Tailscale Serve reference](https://tailscale.com/docs/reference/tailscale-cli/serve)).
  Thus host-loopback port publishing can continue to support an incoming Serve
  path while the guard regulates only application-originated output.

## Design to verify

1. The guard atomically installs a deny-first `inet` output policy before it
   reports healthy. The app starts only after that healthcheck. The app receives
   no `NET_ADMIN`, so it cannot add an allow rule or remove the guard policy.
2. The private inference permission is an exact destination-IP and TCP-port
   tuple. Public traffic is limited to TCP 80/443 and vetted address ranges.
   Grants expire after 5 seconds and the guard renews them every 1 second.
   Both IPv4 and IPv6 need enforcement.
3. The output chain must test those current permission sets for **every**
   outbound packet. In particular, it must not put a broad `ct state
   established,related accept` rule ahead of the tuple checks: doing so would
   let an established connection survive permission expiry. Expiry consequently
   drops later packets on an existing socket; it does not promise to destroy the
   socket or its conntrack entry.
4. A DNS-only allowance for Docker's embedded resolver runs at output
   priority -150, after conntrack at -200 and before Docker's DNS destination
   translation at -100. This lets reply-direction matching use connection
   tracking while DNS still has its original destination. The
   [Netfilter hook priorities](https://wiki.nftables.org/wiki-nftables/index.php/Netfilter_hooks#Priority_within_hook)
   define that ordering. It is restricted to the embedded-resolver destination and DNS
   transport/port. The general output deny policy then remains applicable to
   all other resolver choices and to the subsequent application connection.
   The exact priority interaction with Docker-generated rules is an
   implementation detail that must be validated on the supported Engine/kernel
   versions; Docker does not promise a public numeric priority for those rules.
5. Public DNS answers can change, but the guard never permits a non-public
   address merely because DNS returned it. The application separately vets
   every web/PDF answer and connected peer. The private inference exception is
   an IP literal, not a hostname followed to new addresses. The policy denies
   special/local ranges and operator-configured host public IPs/CIDRs. Any
   exceptional local destination is an approved, expiring exact IP-and-port tuple. The IANA
   registries are the authoritative starting point for IPv4 and IPv6
   special-purpose space
   ([IPv4 registry](https://www.iana.org/assignments/iana-ipv4-special-registry),
   [IPv6 registry](https://www.iana.org/assignments/iana-ipv6-special-registry)).
6. Because the app shares the guard's namespace, the two services are a
   recreation unit. A guard replacement must coordinate app stop/recreate and
   fresh health gating; relying on `depends_on.restart` alone does not cover a
   runtime guard crash. If the guard process is stale or dies, already-loaded
   rules remain deny-first and its unrenewed permissions expire, failing closed.

## Docker DNS forwarding

The tagged [Moby resolver configuration](https://github.com/moby/moby/blob/docker-v29.7.2/daemon/libnetwork/internal/resolvconf/resolvconf.go) marks inherited host nameservers `HostLoopback: true`. The [resolver's `dialExtDNS`](https://github.com/moby/moby/blob/docker-v29.7.2/daemon/libnetwork/resolver.go) dials those in the host namespace. Explicit container or daemon DNS overrides instead use `Sandbox.ExecFunc`, which enters the sandbox namespace. Those upstream requests would be blocked by this guard. The supported installation therefore keeps host-inherited upstreams and does not add direct upstream DNS exceptions.

The [namespace-local resolver NAT setup](https://github.com/moby/moby/blob/docker-v29.7.2/daemon/libnetwork/resolver_unix.go) translates `127.0.0.11:53` to a random listener port after the guard's pre-DNAT check, then translates replies back to source port 53. The disposable checks must exercise real Docker DNS replies, not assume the reply uses its original source port at every hook. These forwarding facts come from tagged source; no external DNS or provider request was made for this research.

## Browser and loopback boundary

Namespace sharing also shares loopback. It is therefore unsuitable for
isolating a browser DevTools/CDP listener from the application: a process in
the shared namespace can address a loopback listener in that namespace. The
future #25 browser design remains disabled here: it needs a **distinct network
namespace** and a public-only egress policy. This issue does not enable or
claim CDP isolation.

## Limits and threat boundary

This design enforces packets while they remain in the container network
namespace. It does **not** protect against:

- a compromised host, Docker daemon, or privileged guard;
- a later trusted host/router NAT rewrite that changes a permitted public
  destination into a local service (the namespace-local output hook observes
  the pre-rewrite destination);
- unknown host public addresses unless the operator supplies them as deny
  IPs/CIDRs; or
- Docker versions or network modes that have not passed the disposable
  rule-ordering and recreation checks.

Accordingly, numeric DNS filtering and operator-maintained known-host-public
CIDR denies reduce public-alias/hairpin risk but cannot prove its absence under
the constraint against host firewall or route changes. Host-level enforcement
or a topology that eliminates the hairpin path would be required for that
stronger guarantee.
